БЕЗОПАСНОСТЬ VENTSEARCH — ЧТО СДЕЛАНО И ЧТО НУЖНО ПЕРЕД ОНЛАЙН-ДОСТУПОМ
=========================================================================

Документ отвечает на два вопроса: «что уже защищает данные пользователей»
и «что обязательно сделать руками перед публикацией сайта в интернет».


-------------------------------------------------------------------------
1. РОЛИ: КТО ЧТО МОЖЕТ
-------------------------------------------------------------------------
В системе три роли. Роль хранится в базе, а НЕ в токене браузера: даже если
у сотрудника на руках старый токен, права проверяются по базе при каждом
запросе — понижение роли действует мгновенно, перевыпуск токена не нужен.

  КЛИЕНТ (user) — по умолчанию у всех, кто зарегистрировался сам.
      Каталог, подбор, сравнение, свой проект. Ничего чужого не видит.

  МЕНЕДЖЕР (moderator) — рабочий доступ сотрудника.
      Всё, что у клиента, плюс: вкладка «Сборки», админ-панель в части
      каталога (правка карточек, перечитать CSV, диагностика).
      НЕ может: смотреть список пользователей, менять чужие учётки,
      раздавать роли. Проверено: эти запросы возвращают 403.

  АДМИНИСТРАТОР (admin) — всё вышеперечисленное плюс люди:
      учётные записи, вкладка «Команда», назначение и снятие ролей.

Ответ на вопрос «хватит ли одной админской учётки на трёх менеджеров»:
НЕТ, так делать не надо. Общий логин — это потеря следов (непонятно, кто
что поменял), общий пароль, который нельзя отозвать при увольнении одного
человека, и лишние права у всех сразу. Правильный порядок:
  1) каждый коллега регистрируется сам на сайте (обычная регистрация);
  2) главный менеджер входит как администратор → админ-панель →
     вкладка «Команда» → «Назначить сотрудника» → находит коллегу по
     ФИО/e-mail → «Назначить менеджером».
Снять доступ — там же, кнопкой «Снять доступ». Никакие файлы править не
нужно, всё делается из интерфейса.

Встроенные защиты от типовых ошибок (проверены тестами):
  - нельзя менять СВОЮ роль (иначе легко случайно потерять админку);
  - нельзя снять последнего администратора;
  - системный аккаунт из ADMIN_EMAIL защищён от смены роли и удаления.


-------------------------------------------------------------------------
2. ЧТО УЖЕ РЕАЛИЗОВАНО В КОДЕ
-------------------------------------------------------------------------
Пароли          - bcrypt с солью. В базе хранится только хеш; в ответах
                  API поля password_hash нет вообще (проверено).
Вход            - JWT (HS256), срок жизни задаётся JWT_EXPIRE_HOURS.
Перебор пароля  - ограничитель попыток по паре «IP + e-mail», при
                  превышении 429 с заголовком Retry-After.
Отключение      - у аккаунта есть флаг is_active: отключённый сотрудник
                  не войдёт и не сможет пользоваться старым токеном.
Права           - проверяются на сервере на каждом эндпоинте, а не в
                  браузере. Спрятанная в интерфейсе кнопка — не защита;
                  здесь закрыт сам API.
SQL-инъекции    - все запросы параметризованы (psycopg2), пользовательский
                  ввод никогда не склеивается со строкой SQL.
XSS             - значения, попадающие в HTML, экранируются.
Заголовки       - X-Content-Type-Options: nosniff, X-Frame-Options: DENY
                  (защита от кликджекинга), Referrer-Policy,
                  Permissions-Policy; в production ещё и HSTS.
Документация    - /docs, /redoc, /openapi.json автоматически отключаются
                  при APP_ENV=production (не отдаём карту API наружу).
Секреты         - при APP_ENV=production сервер ОТКАЗЫВАЕТСЯ стартовать,
                  если JWT_SECRET или ADMIN_PASSWORD остались
                  стандартными. Лучше не подняться, чем работать с дырой.


-------------------------------------------------------------------------
3. ОБЯЗАТЕЛЬНО ПЕРЕД ПУБЛИКАЦИЕЙ В ИНТЕРНЕТ
-------------------------------------------------------------------------
[ ] В secrets\.env.prod задать:
        APP_ENV=production
        JWT_SECRET=<длинная случайная строка, минимум 32 символа>
        ADMIN_PASSWORD=<стойкий пароль администратора>
        ADMIN_EMAIL=<реальная почта главного менеджера>
        DATABASE_URL=<строка подключения с отдельным паролем>
        CORS_ORIGINS=https://<ваш-домен>
    Сгенерировать секрет можно так:
        python -c "import secrets; print(secrets.token_urlsafe(48))"

[ ] Поставить HTTPS (сертификат Let's Encrypt) и закрыть доступ по http.
    Без HTTPS пароли и токены идут по сети открытым текстом.

[ ] Не публиковать сервер напрямую: поставить перед ним nginx (или
    аналог), а uvicorn слушать только на 127.0.0.1.

[ ] Закрыть PostgreSQL от внешней сети (слушать localhost), пароль базы
    отличный от админского.

[ ] Сменить пароль встроенного администратора после первого входа и
    убедиться, что secrets\ не попал в git (он в .gitignore).

[ ] Настроить резервное копирование базы (pg_dump по расписанию):
    учётные записи и проекты клиентов живут только там.

[ ] Проверить, что каталог и цены действительно можно показывать наружу.
    Если нет — использовать DEMO_MODE=1 либо оставить сайт во внутренней
    сети / за VPN.


-------------------------------------------------------------------------
4. ЧТО СТОИТ СДЕЛАТЬ ДАЛЬШЕ (не блокирует запуск)
-------------------------------------------------------------------------
- Подтверждение e-mail при регистрации: сейчас зарегистрироваться может
  любой с любым адресом. Роль у него будет «клиент», но если сайт
  публичный — почту лучше подтверждать.
- Восстановление пароля («забыли пароль») — сейчас пароль меняет админ.
- Журнал действий сотрудников (кто и когда правил карточку, менял роли).
- Двухфакторная аутентификация для администратора.
- Ограничение частоты запросов не только на вход, но и на API в целом
  (проще всего — на уровне nginx).
